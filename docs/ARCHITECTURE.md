# Architecture — YouTube AI Clip Generator

## 1. Requirements summary

| # | Feature | Where it lives |
|---|---------|----------------|
| 1 | YouTube URL input | Frontend form → `POST /api/jobs` |
| 2 | Video info extraction | `services/youtube.py` (yt-dlp metadata, no download) |
| 3 | Audio transcription | `services/transcription.py` (faster-whisper, word timestamps) |
| 4–5 | AI highlight detection | `services/highlights.py` (Claude, structured JSON output) |
| 6 | 20–30 s clips | `services/clip_boundaries.py` (sentence-aligned boundaries) + `services/media.py` (FFmpeg) |
| 7 | Subtitles | `services/subtitles.py` (word-level `.ass` + `.srt`) |
| 8 | Vertical 9:16 | `services/reframe.py` (OpenCV face detection → smoothed crop path → FFmpeg) |
| 9–10 | Preview / download | `GET /api/clips/{id}/video` (HTTP range streaming) + React player |
| 11 | Processing history | `jobs` table + `GET /api/jobs` + History page |

Non-functional: long videos must not block HTTP requests (Celery), every stage must be
restartable, API keys come only from environment variables, and errors must be reported
to the user with a clear message.

## 2. System overview

```
┌──────────────── React + Vite + Tailwind (frontend/) ─────────────────┐
│ URL form → Job progress (polling) → Clip gallery (preview/download)  │
│ History page                                                         │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ HTTP JSON  (/api/*, proxied by Vite in dev)
┌──────────────────────────────▼──────────── FastAPI (backend/app) ────┐
│ api/routes  →  schemas (Pydantic)  →  services / db                  │
│ Creates jobs, reads status, streams clip files                       │
└───────────┬────────────────────────────────────┬─────────────────────┘
            │ enqueue task                       │ SQLAlchemy
    ┌───────▼───────┐                     ┌──────▼──────┐
    │ Celery broker │                     │ PostgreSQL  │  jobs, clips,
    └───────┬───────┘                     └──────▲──────┘  transcripts
            │                                    │
┌───────────▼──────────── Celery worker (backend/app/worker) ───────────┐
│ pipeline: download → extract audio → transcribe → detect highlights   │
│           → build boundaries → render clips (cut, 9:16, subtitles)    │
│ Writes progress to the DB after each stage                            │
└───────────┬───────────────────────────────────────────────────────────┘
            │ files
      storage/jobs/<job_id>/...   (local disk; S3-compatible later)
```

The API and the worker share the same Python package (`app`), settings and DB models;
they are just started with different commands.

## 3. Processing pipeline (state machine)

```
queued → fetching_info → downloading → extracting_audio → transcribing
       → analyzing → rendering → completed
                     (any stage) → failed   (error message stored on the job)
```

| Stage | Tool | Output |
|-------|------|--------|
| fetching_info | yt-dlp (`download=False`) | title, channel, duration, thumbnail → `jobs` row |
| downloading | yt-dlp | `source.mp4` (≤1080p) |
| extracting_audio | FFmpeg | `audio.wav` (16 kHz mono) |
| transcribing | faster-whisper (`word_timestamps=True`) + VAD | `transcripts` table (words + sentences, JSONB) |
| analyzing | Claude via `claude -p` (`claude-opus-5-5`) | ranked candidates as **sentence-ID ranges** |
| rendering | FFmpeg + OpenCV | `clips/<n>.mp4`, `.ass`, `.srt`, thumbnail |

Key decisions:

- **The LLM never writes timestamps.** It returns sentence IDs; code maps them to word
  times from Whisper. This prevents invented timestamps and guarantees clips start and end
  on whole sentences.
- **Boundaries are snapped to sentence ends and silences**, then fitted to 20–30 s by adding
  or removing whole sentences.
- **Overlapping candidates are removed** (keep the higher score when overlap is above 30%).
- **Each stage is idempotent**: if its output file already exists the stage is skipped, so a
  failed job can be retried without redoing the download or transcription.
- **Titles and descriptions** are generated by a cheaper model (`claude-haiku-5-5`).

## 4. Data model (PostgreSQL)

```
jobs
  id (uuid, pk)          youtube_url        youtube_video_id
  title  channel  duration_seconds  thumbnail_url
  status (enum above)    progress (0–100)   stage_message   error_message
  created_at  updated_at  completed_at

transcripts
  job_id (fk, unique)    language   duration_seconds
  sentences (jsonb)      words (jsonb)

clips
  id (uuid, pk)   job_id (fk)   rank
  start_seconds   end_seconds   duration_seconds
  title  description  hashtags (jsonb)  category  viral_score  reason
  transcript_text
  video_path  subtitle_path  thumbnail_path
  status   created_at
```

Rule: **routes stay thin.** They validate input, call a service, and return a schema.
Services are plain Python functions or classes with no FastAPI imports, so the Celery
worker can reuse them and they can be tested on their own.

| Service | Used for | Cost |
|---------|----------|------|

## 9. Limitations

**Legal / YouTube**
- YouTube's Terms of Service forbid downloading videos without YouTube's permission.
  yt-dlp works technically, but using it is a ToS violation. The official Data API has
  **no** download endpoint.
- Re-posting clips of other people's videos is usually copyright infringement; fair use is
  narrow and decided case by case. Platforms' Content ID will detect re-uploads.
- Intended use: **creators repurposing content they own or have permission to use.** If the
  app is made public, add an ownership confirmation and a DMCA takedown process, and
  consider a file-upload path that does not depend on YouTube.

**Technical**
- yt-dlp breaks when YouTube changes its player. Keep it updated (`pip install -U yt-dlp`).
- YouTube blocks or throttles datacenter IPs and sometimes requires cookies (age-restricted
  or "confirm you're not a bot"). `YTDLP_COOKIES_FILE` is supported in config.
- CPU transcription is slow (about 0.3–1× real time with the `small` model). A CUDA GPU with 6 GB or more
  makes `large-v3` practical.
- Celery's default worker pool does not support Windows; run the worker with `--pool=solo`.
- Windows Smart App Control blocks some native DLLs (psycopg, Rollup's native module,
  Memurai's installer). The project uses pg8000, Rollup's WebAssembly build and a PostgreSQL
  Celery broker instead, so everything runs natively on Windows without WSL.
- Face-based reframing works well for talking heads, less well for screen shares or wide
  shots (falls back to a center crop).

## 10. Claude access (CLI instead of API key)

All LLM calls go through `app/services/llm.py`, which runs the Claude Code CLI headless:
`claude -p --output-format json --json-schema <schema> --tools "" --setting-sources ""
--strict-mcp-config --no-session-persistence`. The prompt is sent on stdin, the CLI
validates the reply against the JSON schema, and the result is read from
`structured_output`. `ANTHROPIC_API_KEY` is removed from the child environment so the
subscription login is always used.

- Subscription login is for personal use. Offering the app to other people requires an
  API key (the client is behind one interface, so an API provider can be added later).
- Each call takes a few seconds to start; the pipeline makes only a handful of calls per video.
- Calls count toward the subscription's usage limits; a limit error fails the job with a
  clear message, and the job can be retried later.

## 11. Reliability: progress, resume and interrupted jobs

- **Progress**: each stage reports its own 0–1 progress through `StageContext.report`, which
  maps it onto the job's overall percentage (by stage weight) and saves at most every 1.5 s.
- **Idempotent stages**: download and audio extraction skip work whose output already
  exists and is valid (checked with ffprobe). Audio is written to `audio.partial.wav` and
  renamed when complete, so a half-written file never looks finished.
- **Resume**: yt-dlp keeps `.part` files; a retried job continues the download.
- **Interrupted jobs**: when the worker starts, jobs left in a running status (worker was
  closed or the PC restarted) are marked failed with "interrupted, click Retry". This
  assumes a single worker, which is the Windows setup (`--pool=solo`).
- **Retry**: `POST /api/jobs/{id}/retry` (failed jobs only) re-queues the job.
- **Download size**: 1080p H.264 is about 20–25 MB per minute of video. On a slow
  connection, set `MAX_DOWNLOAD_HEIGHT=720` to roughly halve download time.

## 12. Transcription and sentences

- faster-whisper runs locally with word timestamps, VAD (skips silence and music) and
  `condition_on_previous_text=False` (prevents repetition loops on long audio). The model
  is loaded once per worker process. The first run downloads it (`small` is about 480 MB).
- Audio is passed as a NumPy array read with Python's `wave` module, bypassing
  faster-whisper's PyAV decoder, which breaks between PyAV releases.
- `services/sentences.py` groups words into sentences: split at end punctuation (not at
  abbreviations), at pauses of 1.2 s or more, and split run-ons longer than 20 s or 60 words
  at a comma or the longest pause. Each sentence keeps its word range, so the AI can pick
  sentence IDs and the code converts them to exact word times.
- Speech over loud music: if VAD keeps no words, transcription is repeated without VAD.
- Speed on this laptop's CPU (`small`, int8, greedy decoding): about 1x real time.
- `GET /api/jobs/{id}/transcript` returns sentences (`?include_words=true` adds words).

## 13. Highlight detection (Phase 4)

Two Claude calls per video through `claude -p` (`services/highlights.py`):

1. **Moments** (`CLAUDE_MODEL`, Opus): the prompt holds the video title and the transcript
   as `[S<id> <mm:ss> <duration>] text` lines, wrapped in `<transcript>` and marked as data
   (instructions spoken in a video are ignored). The JSON schema asks for sentence-ID ranges,
   a category and five rubric scores (hook, standalone, payoff, emotion, shareability), for
   up to `clamp(1.5 × minutes, 3, 2 × MAX_CLIPS_PER_VIDEO)` moments.
2. **Titles** (`CLAUDE_FAST_MODEL`, Haiku): one call for all selected clips: title,
   description and hashtags in the transcript's language. Missing entries fall back to the hook.

Between the two calls, pure code (`services/clip_selection.py`) decides the final clips:

- **Fitting**: each range is adjusted to `CLIP_MIN_SECONDS`–`CLIP_MAX_SECONDS` by
  adding or removing whole sentences (never mid-sentence). Moving the start later costs more
  than adding context before it; starting on a context-dependent word ("And…", "That's
  why…") is penalised; the fitted clip must keep at least half of the chosen sentences. If
  nothing fits exactly, up to 2 s shorter or 4 s longer is accepted; otherwise the moment is
  dropped. Padding (0.15 s before, 0.35 s after) never reaches into neighbouring sentences.
- **Scoring**: weighted rubric (hook 30%, standalone 25%, payoff 20%, emotion 15%,
  shareability 10%), minus 0.5 for a dangling start.
- **Selection**: best first; drop clips overlapping a better one by more than 30%; a soft
  per-category cap gives variety, then remaining slots are filled; ranked by score.

Raw AI responses are saved to `storage/jobs/<id>/highlights.json`. Clips are stored in the
`clips` table and served by `GET /api/jobs/{id}/clips`. Measured: about 35–45 s for both
calls on a 3.5-minute video. A Claude error (e.g. a usage limit) fails the job; Retry reuses
the download and transcript.

## 14. Rendering (Phase 5)

Per clip (`services/render.py`), in one FFmpeg pass after a short OpenCV analysis:

1. **Reframe plan** (`services/reframe.py`): sample ~4 frames/s, detect faces with the bundled
   YuNet model (`app/assets`, SHA-256 checked at load), detect scene cuts with colour
   histograms. If a face is found in at least 35% of samples the layout is **track**: per
   scene, gaps are filled, the position is smoothed (1 s moving average) with a 6% dead zone,
   and the camera jumps at cuts. Picking between several faces prefers a large, confident face
   near the current position (quadratic distance penalty), so two similar faces don't cause
   ping-pong. Otherwise the layout is **fit**: the whole frame over a blurred, zoomed copy.
2. **Crop as an expression**: keyframes (simplified within 4 px) become a flat FFmpeg
   expression of `t`, applied by the `crop` filter. The graph is written to a file
   (`-/filter_complex`), so there is no command-line escaping or length limit.
3. **Captions** (`services/subtitles.py`): 1–3 words per caption from word timestamps,
   broken at sentence ends and pauses; one ASS event per word with the spoken word
   highlighted; font chosen by language (Arial; Nirmala UI for Devanagari; YaHei, Yu Gothic,
   Malgun Gothic for CJK) or `SUBTITLE_FONT`. Burned in with libass; `.srt` (CRLF) for download.
4. **Encode**: H.264 (`RENDER_PRESET`, `RENDER_CRF`), 1080×1920, AAC 160 kbps,
   loudness normalised to −14 LUFS (the usual target for short-form platforms), `+faststart`.
   Written to `NN.partial.mp4` and renamed when complete; thumbnail from the result.

Each clip renders independently: a failed clip is marked `failed` with its error and the
others continue; the job fails only if every clip fails. Retry renders only clips that are not
`ready`. Measured on this laptop: about 1.8× the clip length (≈55 s for a 30 s clip).

Files are served by `GET /api/clips/{id}/video` (HTTP range requests for seeking;
`?download=true` for an attachment named after the title), `/thumbnail` and `/subtitles`.

## 15. Job management and UI (Phase 6)

| Method | Path | Purpose |
|--------|------|---------|
| DELETE | `/api/jobs/{id}` | Delete a finished job: files first (a locked file returns 409 and nothing is lost), then rows (transcript and clips cascade) |
| POST | `/api/jobs/{id}/reprocess` | `{"start_from": "highlights"}` drops the clips and asks Claude again; `"render"` re-renders the same clips. Download and transcript are reused |
| POST | `/api/jobs/{id}/free-space` | Delete `source.mp4` and `audio.wav` (and partial downloads), keep clips. A later reprocess downloads the video again automatically |
| GET | `/api/jobs/{id}/clips.zip` | All ready clips, `.srt` files and `captions.txt` (titles, descriptions, hashtags). Built in a temp file, deleted after sending |

All of these require a finished job (409 while running). Jobs include `clip_count`,
`ready_clip_count`, `storage_bytes`, `has_source_files` and `failed_stage` (the stage a failed
job was in, also recorded for interrupted jobs); `GET /api/jobs` adds `storage_bytes_total`.

On retry or reprocess, the info stage reuses the saved title and duration (no YouTube call)
but still applies the current limits.

UI: the job page has a stage stepper, an actions bar (Retry, Download all as ZIP, New
highlights, Re-render, Free up space, Delete) and clip cards that appear while clips are
rendering. Each card has a vertical player and download buttons. History shows clip count
and disk use per job, total disk use, delete, and refreshes itself while jobs are running.
